Roadmap

Roadmap

Generics and interfaces

The design of type parameters, constraints, interfaces, Self, changes self and iterables, and the parts that are still to come.

Generic functions and structs, constraints with with, interfaces, Self, changes self, interfaces as &Shape borrows, generic interfaces and Iterable all work. Their rules and examples are in Generics, and the lesson and guide introduce them. This page keeps the design and marks the parts the compiler does not accept yet.

Generic functions and structs

Type parameters are written in <>, inferred from the arguments, and each call makes its own function. See Generic functions, Working out the type parameters and Generic structs and enums.

Constraints with with

T with Shape asks for a type that implements an interface, and T with Shape and Drawable for several. See Constraints.

Interfaces

An interface lists method signatures, static methods and required fields. A struct says which interfaces it implements with with, several joined by and, and extends builds one interface on others. See Interfaces and Generic interfaces.

Self, and methods that change self

Self names the implementing type inside an interface, and changes self marks an interface method that may change self. See Self and Methods that change self.

Interfaces as types

An interface is borrowed, never held: &Shape accepts any struct that implements it, and the method that runs is picked while the program runs. See Interfaces as types.

Iterables

Iterable<T> has one method, T? at(uint64 i), and for walks it. See Iterable.

Types you do not own

Numbers, bool and string promise the standard interfaces Zero, Equal, Ordered and Text already. Any type can promise an interface from outside its declaration. This is the first attempt and is tentative: see Types you do not own.

Still to come

These parts are designed but not built. Each carries its own marker.

Constraints on unitsNot implemented yet

A unit parameter with a constraint, unit U with Shape, is E0901 today. The spelling is open: an interface over units is not designed yet.

Methods with type parameters of their ownNot implemented yet

A method may have type parameters only through an interface method, so that every extra parameter is visible in the interface:

A struct's own methods use only the struct's parameters. The interface form is E0901 today.

Borrowing a generic interfaceNot implemented yet

&Read<uint32> is E0901 today: a generic interface can be implemented and used through a constraint, but not yet through a borrow.

Calculations on value parameters

A value parameter (see Value parameters) can be used in a calculation inside a type: T[N + 1] as a field, or Buffer<T, N * 2> as a type argument. The calculation is worked out for each instance. See Named constants and calculations.

Exclusive parametersNot implemented yet

none show(exclusive &Shape s) would accept only a value whose interface is exactly Shape, with no upcast from Shape3D. The word exclusive is E0901 today, and its details are still to design.

Returning a function valueNot implemented yet

A function value only goes down: it can be a parameter, a local or be called. Returning one, or storing it in a struct or list, is E0652 by design, and a way to keep one (a move lambda, for example) is not designed yet. See Function types and lambdas.

Errors with fails and maybe

failure types, fail, maybe, fails with, catch-alls and chained causes. There is no Result type.

Collections

Arrays, lists and maps as designed, the settings that will change lookups, and the parts still to come.
