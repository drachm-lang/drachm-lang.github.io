Reading compiler errors

How a Drachm error is laid out, what the codes mean, and a worked fix for each family of mistakes.

Everyone writes programs the compiler rejects, so reading its messages is a skill worth learning early. Drachm messages are built to be read from the top: the first line says what is wrong, the arrows say where, and the help line says what to write. This guide takes one message apart, then walks through one real mistake from each family and its fix.

You can follow along with drachm check file.drh, which reports problems and builds nothing.

The shape of a message

Every message has the same parts. This one comes from adding a number to a string.

The first line is the headline: a severity (error or warning), a code in brackets, and a short title. The code never changes, so you can search for it or ask the compiler about it.

The location gives file, line and column. Many editors turn it into a link.

The source lines quote your code. A label under ^^^ marks the exact place that is wrong, and a label under --- marks related code, here the left side of the +. Labels say what the compiler knows about the spot, such as a type.

A note explains a rule, and a help line proposes a fix. Not every message has both. When help shows code in backticks, you can usually paste it.

The last line counts the errors and warnings in the file. The compiler reports everything it finds in one run, so fix from the top and recheck.

Errors and warnings

The letter in the code is the severity. An E code is an error: the program does not compile, and drachm check exits with code 1. A W code is a warning: the program still compiles and runs, and the message is printed first. Treat warnings as errors you have not been forced to fix yet. They point at code that probably does not do what you meant.

This program has two warnings and no errors, so check exits with 0.

What the digits mean

The first two digits of a code name the family of the problem, and they tell you where to look.

CodesFamily
00xxsyntax: the text is not Drachm
01xxtypes, conversions, match, control flow
02xxnames, declarations, mut
03xxownership: moves, copies, borrows
04xxunits of measure
05xxenums
09xxvalid Drachm that this compiler cannot do yet

Syntax: the text is not Drachm

Syntax errors are E00xx. The compiler found something it could not read. The one to know is E0003, "unexpected token". Here a ; is missing at the end of line 4.

The compiler only notices the problem when it reaches the next line, because uint32 hp = 3 could still continue. So the arrow points at the start of the next statement, and the real mistake is at the end of the line before it. When a syntax error looks wrong, read the line above.

The fix is to end line 4 with ;.

Types: a value of the wrong kind

Type errors are E01xx. Drachm never converts between unrelated types for you, so the compiler says what it expected and what it found. The common case is a number where text is wanted, as in the first example above, and the help line already has the fix.

Conditions are strict too. A number is not a bool, and the message says so.

Say what you mean instead: if (a != 0). Number mistakes are covered in more depth in Numbers without surprises.

Names: something does not exist

Name errors are E02xx. E0201 means a name or function is not known at that point. Usually it is a typo, a missing in io;, or a binding declared in a different block. Two typos give two errors, because the compiler keeps going.

There is no help line here, because the compiler cannot know which name you meant. Compare the spelling against the declaration, and check that the name is in scope.

Control flow: a path with no answer

Control flow errors live in the 01xx group as well. A function that promises a value must give one on every path. Here sign returns only when n is negative, so for any other n the function would run off its end.

The label sits on the function's head, not on a line in the body, because the problem is the whole function and not one statement.

Ownership and borrowing: who owns what

Ownership errors are E03xx, and they are the ones most new readers find odd, because the rule is new. A string has one owner. Writing string b = a; moves the text to b, and a has nothing in it afterwards. The labels show the whole story in order: the move, then the later use.

The second error is a borrow. &c lends a read-only view of c, and while the view is still going to be used, c must not change. The label on the last line says the borrow is still used here, which is what makes the change illegal.

The first fix is the one in help: string b = copy a;. The second is to print q before the assignment, so the borrow ends first. See Ownership and Borrowing for the ideas behind these.

Units: the dimensions do not match

Unit errors are E04xx. They are the compiler doing its job: you cannot add metres to seconds, and a plain number has no unit. The first error shows two labelled operands. The second tells you how to give the number a unit, and shows the exact text to write.

See Units of measure in practice for more.

A routine for fixing errors

  1. Fix the first error first. Later errors are sometimes caused by it.
  2. Read the headline, then the label under the ^^^. Together they usually say what the compiler saw.
  3. Read note for the rule and help for the fix, and try the fix.
  4. Run drachm check again. It is quick, and it shows what is left.
  5. If the message is still unclear, run drachm explain with the code.
