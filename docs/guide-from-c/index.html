Coming from C or C++

What the compiler does for you that you did by hand, how ownership replaces malloc and free, and what unsafe and raw pointers still give you.

Drachm compiles to native code and aims for C's speed, so a lot will feel familiar: fixed-size integers, structs, functions that return their type first, a main, and a compiler that does not hide what the machine does. What differs is who looks after the dangerous parts. This guide lists what you stop doing by hand, and what you keep when you really want it.

Cleanup that cannot be forgotten

A value that owns something is cleaned up at the end of its scope, whichever way the scope is left: running off the end, return, break, continue or skip. If a struct has a method named drop, it runs then, like a C++ destructor, but there is no copy constructor to get wrong, because values are moved or copied explicitly.

The reserved name drop() runs when the value is destroyed.

scratch is declared inside find.

return i leaves the function in the middle of the loop. The output shows scratch released before found 8 is printed.

At the end of main, values drop in reverse order of declaration, b and then a, as C++ destructors do.

You can run the cleanup earlier with destroy a;, which runs drop() now and ends a. Calling a::drop() yourself is an error. See Moves and copies for what the compiler does with a struct that has a drop.

Integers

Sizes are in the name, so there is no int to depend on. Overflow wraps, signed and unsigned alike, so the compiler never assumes that an overflow cannot happen. Division by zero and an out-of-range string index are not undefined: the program stops with a message and exit code 101.

A conversion that can lose information (uint32 to uint8) compiles with warning W0102 until you write x::to<uint8>(). Bitwise operators need parentheses next to arithmetic and comparisons, which removes the classic a & b == c surprise.

Ownership replaces manual memory management

C++ has unique_ptr and RAII as conventions. Drachm makes the rule part of the language and checks it at compile time, so no program can free something twice or use it after the free.

  • A value has exactly one owner. Assigning it or passing it moves it.
  • Using the old name afterwards is error E0301.
  • copy x makes a second value, and you always write it. Nothing copies silently except small plain values: numbers, bools and structs of them up to 32 bytes.
  • Lending, instead of moving, is a borrow: &T for reading (many at once) or &mut T for changing (only one, and nothing else reads meanwhile). Both are written at the call: show(&p), bump(&mut n).

A &mut parameter is the safe form of the int *out parameter. Reads need no *, and assigning writes through to the caller's variable.

Two out-parameters. q = a / b; writes through the borrow, since the right side is not itself a reference.

&mut is written at the call, and only a mut binding can be lent that way.

Overflow wraps for both signed and unsigned numbers.

The compiler also stops the dangling pointer. A borrow cannot outlive the value it points to, and a function that returns a borrow says which parameter it comes from with lives when that is not obvious. See Borrowing and Borrows and lifetimes.

What unsafe and raw pointers still give you

Sometimes you need an address and nothing checks it for you: talking to hardware, building a data structure the borrow checker cannot see, or porting C. Raw pointers exist for that, and every use is fenced.

  • A file that uses them starts with //--!$unsafe: true, or the project says unsafe = true under [native] in drachm.toml. Without either, the compiler refuses (E0317).
  • *T is a pointer you can write through, *fixed T one you can only read. Both are 8 bytes. address of n makes one.
  • Making, copying, comparing, reading and writing through a pointer all need an unsafe { } block. A function marked unsafe counts as one block, and calling it needs a block.
  • A pointer can be none, and p == none is the null check.
  • The compiler does not track a pointer: it must not outlive the thing it points to, and that is your job again.

There is no pointer arithmetic or malloc in the compiler yet, so this is for pointing at values you already have.

An unsafe function. The body needs no inner block.

The call needs unsafe { }. none is a null pointer.

The full rules are in Unsafe and pointers and lesson 11.

AssemblyNot implemented yet

A whole function may be written in assembly, with no mixing of assembly into other functions. The register mapping and syntax flavour are still open.

What -O does

Drachm has two backends, and the one you pick changes speed, never meaning.

  • A plain build goes through Cranelift and compiles in milliseconds.
  • -O writes C and calls your system C compiler (cc, or clang on Windows), then links the result with the small runtime. Your program gets everything that compiler does at its best, which is why -O runs at C speed.

Tests build every program both ways and compare the output bit for bit, so a program that behaves differently between them is a compiler bug. You need a C compiler installed to link either way. Performance has numbers.

Importing C headers

Existing C libraries are called by importing their header like a module, with every name behind a prefix:

The compiler reads the header with libclang. sdl::SDL_Init(...) is the C function, sdl::SDL_Rect the C struct with its exact layout, and sdl::SDL_INIT_VIDEO the macro's value. C calls need unsafe; you write a small Drachm wrapper that checks what C needs and gives the rest of the program a safe signature. int and long are c::int and c::long, types of their own that you convert with as; char * is a foreign *uint8, and p::text() turns it into a string. What a C function returns is released by the wrapper, in drop(), never automatically. See Calling C libraries.

What is not here

  • No preprocessor or macros. Constants and functions do that job.
  • No implicit conversion between a number and a bool.
  • No goto. break 2; leaves two loops, and skip leaves if blocks. See Control flow.
  • No header and source split. Modules are designed for step 7.
  • No inheritance or virtual tables. Interfaces and generics (Generics) are designed.
  • Templates become generics, which are designed but not built.
