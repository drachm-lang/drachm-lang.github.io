Testing your programs

Using check, run and build, exit codes, writing expected-output tests the way the compiler's own repo does, and the test keyword with drachm test.

Today you test a Drachm program by running it and comparing what it prints. This guide shows the commands, what the exit codes mean, and the expected-output technique the compiler's own repository uses for over two hundred programs. At the end is the test keyword, which runs with drachm test.

Three commands

  • Use check while you edit. It is the fastest feedback and runs nothing.
  • Use run to try the program. It passes your standard input through, so printf '4\n5\n' | drachm run sum.drh works.
  • Use build (with -o NAME and -O if you want) when you need the executable, for example to run it many times in a script. Add -O to test the optimised build too: both builds must print the same, and a difference means a compiler bug worth reporting. See Command line.

Exit codes

Every step ends with an exit code, and 0 means success.

a run-time fault: division by zero, string index out of range101
a failure leaves mainthe failure's exit code, 1 if it has none

Expected-output tests

A test is a program plus a file saying what it must print. The compiler's repository tests itself this way: there is a folder of small programs, and for each one cargo test builds it, runs it and compares the output.

The files this repo uses

The compiler's own test runner (tests/run.rs) follows the same idea and has a few more files beside the program. Every one is optional except the .out.

FileMeaning
NAME.drhthe program
NAME.outwhat it must print on stdout, exactly
NAME.inits standard input. Without it, input is empty, so a test never waits for a terminal
NAME.codethe exit code it must end with. Without it, 0
NAME.errlines that must each appear somewhere in the program's stderr
NAME.warnlines that must each appear in the compiler's own output. Without it, the compiler must print nothing at all

For a program that is expected to fail to compile, a different folder is used: tests/fail/NAME.drh with a NAME.err listing the error text that must appear. It matches the code and message, not the layout. For example, badmain.err holds the error code line and the cause for a main of the wrong shape.

A test of a run-time fault is the same as any other. The division by zero case is a program, an .out of what printed first (before), a .code file holding 101, and an .err file with the panic message.

Two habits from the repo are worth copying:

  • Every run test is built both plain and -O, and the outputs are compared.
  • The tests run with leak checking on: a string that is never freed, or freed twice, fails the case.

The test keyword

A test block can sit in any file, next to the code it checks. Its body is ordinary code, and assert(condition); stops the test when the condition is false (see assert):

What the rules are:

  • Each test is built and run as a program of its own. A test passes when its program exits with 0. The output of a test is shown only when it fails.
  • Test names are unique within a file (E0239).
  • expect failure checks a failing call inside a test (see below).
  • A normal build or run checks the test blocks too, so a broken test is an error in every build. It leaves their code out of the executable: only main is built. drachm test builds each test.
  • drachm test works on a library as well as a program, and -O runs the tests on the optimised build.
  • The exit code is 0 when every test passes and 1 otherwise.
  • A test block in a script that also has top-level statements is not supported yet (E0901). Put the tests in a file with main, or in a project.

An assert can name what it checks, after the condition: assert(add(2, 3) == 6, "the sum of two and three");. The message is plain text, and a failing check prints it after the condition, for example assertion failed: add(2, 3) == 6: the sum of two and three.

Expecting a failure

Some code must fail, and a test should check that it does. expect failure names the failure a call must end with:

The test passes when the call fails with ConvertError. Three other outcomes stop the test with a message:

  • the call does not fail at all;
  • the call fails with another failure of the same call;
  • the call can never fail with the named failure (a compile error, E0545).

expect failure is only allowed in a test block (E0014). The call must be one that can fail (E0003 otherwise), and the failure must be a failure type (E0540).
