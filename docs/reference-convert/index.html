Converting

The convert module: numbers in other bases, the bytes of a text, and JSON built from a struct's field names.

The convert module changes a value from one representation into another. Import it with in convert; and call a function as convert::name(...). It holds three kinds of functions: numbers as text in a base, the bytes of a text, and JSON. Turning one number type into another is not here; that is value::to<T>(), described in Numbers.

Bases

convert::hex(n), convert::binary(n) and convert::octal(n) take a whole number of any width and give its digits as text, in lower case, with no prefix. A negative number has a minus sign in front: convert::hex(-255) is -ff.

convert::fromHex(text), convert::fromBinary(text) and convert::fromOctal(text) read digits back into a whole number. The result takes its type from where the value goes, like other conversions: uint8 b = convert::fromHex("ff") fails; reads the text as a uint8. This works for a declaration, an assignment, an argument and a return. When nothing says which type is wanted (the value is only printed, say) the result is a uint64.

The digits can be capitals or not. A prefix is allowed: 0x for hex, 0b for binary and 0o for octal. A signed type also accepts a minus sign in front, before the prefix: sint8 low = convert::fromHex("-0x80") fails;. Spaces and separators are not digits. Anything that does not read fails with ConvertError, the failure that text::to<T>() uses:

VariantWhen
Emptythere are no digits: the text is empty, or only - or a prefix
NotANumbera character is not a digit of the base
OutOfRangethe value does not fit the type, which includes any minus sign for an unsigned type (-0 is fine)

The functions only read the text, so a variable passed to them can be used afterwards.

Bytes

convert::utf8(text) gives the bytes of a text as a uint8[?]. A character outside ASCII takes two to four bytes, so the list can be longer than text::len().

JSON

convert::toJson(value) gives the JSON text of a value as a string, and convert::fromJson<T>(text) reads a T back from JSON text. T is a struct, an enum, a map or a list. The compiler builds both from the field names and types of T, so there is nothing to write for a new type. The value passed to toJson is only read, and the text passed to fromJson is borrowed, so both can be used afterwards.

The output is compact, with the fields in the order they are declared and no spaces: {"name":"Ada","level":7}. Every field is written, whether it is public or not. There is no pretty-printed form.

DrachmJSON
whole numbersa number, written in full (uint128 too)
float32, float64a number; NaN and infinity are written as null
booltrue or false
stringa string, with ", \ and control characters escaped
T?null for none, otherwise the value
T[?]an array
a structan object with one entry per field
an enum variant with dataan object with one entry, the variant's name, holding an object of its fields: {"Circle":{"radius":2.0}}
an enum variant without datathe variant's name as a string: "Calm"
Map or OrderedMap with string keysan object, in the order the map holds its entries
a map with other keysa list of [key, value] pairs: [[7,"seven"],[300,"three hundred"]]

Reading is strict. The text has to be one JSON value, and it has to fit the type:

  • a whole number is written without a fraction or exponent, and has to fit the field's type: 256 for a uint8 is an error, not a wrap;
  • an integer is accepted for a float field;
  • an object has exactly the fields of the struct. A missing field is an error, except for a field that is an optional, which becomes none (and so does a null); a field the struct does not have is an error;
  • an enum is read from a string naming a variant without data, or from an object with one entry naming a variant with data; any other variant name is an error that lists the variants. The fields of a variant follow the rules of a struct's;
  • a map with string keys is read from an object, any other map from a list of [key, value] pairs. A key that appears twice in a list of pairs keeps the last value;
  • the escapes of JSON strings are understood, including é and surrogate pairs for characters outside the first plane.

When the text does not fit, fromJson<T> fails with convert::JsonError. Each variant is one cause, and the message names the place in the text, starting from $:

VariantMessage
Syntax(detail)invalid JSON: expected ... at line 1, column 2
WrongType(path, expected)$.items[2].name should be text
MissingField(path)$.home is missing
UnknownField(path)$.extra is not a field of the type
OutOfRange(path)$.level does not fit its type

The call needs maybe, fails or a handler like any call that can fail, see Errors. Name the failure as convert::JsonError, or import it with in JsonError from convert;.

Not built yet

JSON is built for structs, lists, optionals and the types in the table above. These are stopped with E0901 when the compiler checks the call, for now: fixed-size arrays, C unions, failures, and a struct or enum that contains itself (an enum with a list of itself, for a tree). Reading a whole number or a string at the top level (fromJson<uint32>(text)) also waits. The same holds for reading a list of bytes back into text, and for numbers wider than 64 bits in fromHex, fromBinary and fromOctal.
