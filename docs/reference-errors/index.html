Failures

failure types, fails, fail, maybe and a bare fails at the call, because, ConvertError, and what happens when a failure leaves main.

A function that can go wrong says so with fails, and every call says what happens when it does. There is no Result type and no unwinding: a failing function returns its failure as an ordinary value, and every value alive in it is dropped on the way out, exactly as for a return. The errors lesson introduces this with exercises, and Error handling without exceptions is about designing with it.

Failure types

A failure is its own kind of declaration. Each variant has a name, optional values in parentheses, a message, and optionally exit N. The message is an ordinary string, so one that uses the variant's values is an f"..." string, and ${name} must name one of the variant's own values (E0551). Exit codes run from 0 to 255 (E0552), and 1 is used when none is written. A failure needs at least one variant (E0554), and its variants have distinct names (E0520).

The values of a variant are numbers, bools and strings for now (E0901 for anything else). A failure value is an ordinary value that moves and is dropped like a struct that owns a string; it cannot be copied.

fails and fail

fails after the parameters lists the failure types the function may end with, in either order with lives. A name that is not a failure type is E0540, and a type listed twice is E0554. Functions, methods and operator methods can fail; so are constructors (see Structs) and drop() (see A drop that fails).

fail X; leaves the function with variant X; fail X(values); gives it values. The name is searched in every listed failure type. If two of them have a variant of that name it is E0543, and fail ParseError::Empty; names the type. A variant none of the listed types has is E0541, and fail in a function with no fails at all is E0542. return in a failing function is a success, and so is reaching the end of a failing none function.

Saying what happens at the call

A call of a function that can fail, with nothing after it, is an error in a project (E0544): the message shows the ways out: a fallback with maybe, passing the failure up with fails, or a handler with fails with. A lone .drh file and a script use the crash setting by default instead: the call stands, and if it fails the program prints the failure's message and stops with its exit code (see Unhandled failures).

call maybe value is the call's result, or the value when it failed. The value is converted to the result type, and it is evaluated only on failure. It is a single value or a parenthesised expression: parse(s) maybe 0 + 1 is E0534, and (parse(s) maybe 0) + 1 is what is usually meant. A call that returns none has no value to fall back to.

A bare call fails passes the failure up: the result is the call's result, or the caller returns the failure. The caller must list every failure type the callee lists (E0548 names the first missing one). Every value alive in the caller, including the temporaries of the statement, is dropped as for a return.

A failing call can be an argument, an operand, an initialiser or a loop condition, as long as it carries its own maybe or fails. For an operator method that fails, put the operation in parentheses first: (a == b) maybe false. a != b with an == that fails takes maybe and fails the same way, and the fallback is the value of the whole !=: (a != b) maybe true. Handlers after such a != are not built (E0901); handle the == instead.

Handlers

call fails with (Type e) => { ... } runs a block when the call fails with that failure type, with the failure moved into e. The ; ends the whole expression. A call that can fail with several types gets one handler for each (E0546 for a repeat, E0545 for a type the call cannot fail with), written one after the other. fails with (any e) takes every failure not named before it, and so does otherwise (any e), which must be last (E0553). If a type is left out and there is no catch-all, E0544 names it. A catch-all after handlers for every type is W0111.

Inside the block, e is an ordinary local that owns the failure; it is dropped at the end of the block unless it was moved. For a handler of any, its type is the failure (one type) or the set of the call's failures. ${e} and e::message() give the message, e::exit() the exit code, and match (e) takes a failure apart with the usual case patterns. e::cause() is not built (E0901).

A handler ends in one of these ways:

  • maybe v; gives the value of the call (converted like any value) and carries on after the call. It is E0550 outside a handler. For a call that returns nothing, write maybe; or simply let the block end.
  • return leaves the enclosing function, and fail ...; raises one of its failures (the function must list it). fail e; raises the failure that was caught again, as long as the function lists its type.
  • break and continue leave or restart the loop around the call.

For a call that returns a value, a block that can end without one of these is E0547.

fails with none; and ignore failure both ignore a failure of a call that returns nothing. A call that returns a value cannot be ignored (E0547): give it a fallback instead.

Because in a handler

fail X because e; works on the failure a handler caught: the new failure keeps its message behind it. e is moved. Only the message and the earlier causes are kept, and the report of a failure that leaves main lists them.

A drop that fails

none drop() fails FlushError { ... } is allowed. Nobody is there to handle a failure of the drop() that runs by itself when a value goes out of scope, so a failure that comes out of it is reported like one that leaves main (error:, the message, the causes) and ends the program at once with the failure's exit code. Values still alive are not dropped first.

Reading text as a number

text::to<T>() fails with the built-in ConvertError, which has the variants Empty (nothing but spaces), NotANumber and OutOfRange (a number that does not fit T). The reading rules are the forgiving ones from Input and output. So the call needs a maybe or a fails:

You cannot declare another item called ConvertError.

Leaving main

main may say fails. A failure that leaves it is printed to standard error as error: and the message, then one because: line for each cause, and the program exits with the failure's code (1 by default). If main returns a number and fails, the failure's code wins; on success the number is the exit code. Everything alive is dropped before the program ends.

Because

fail X because e; raises X and keeps the failure e (a failure value, E0549 otherwise) as its cause: e is moved, and only its message is kept. The report above lists it:

A cause is text, and it is not inspectable. The failure can be one you built yourself or the e of a handler.
